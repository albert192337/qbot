# 公共房间：联机社交房设计

> 日期：2026-08-21
> 状态：草稿（待批准）
> 上游：`2026-08-02-multiplayer-presence-design.md`（1v1 presence，已实现 L0~L2）、
> `2026-08-03-gamification-social-design.md`（游戏化方向，未开工）、
> `2026-08-02-skin-market-design.md`（有状态后端 + 零账号身份的先例）

---

## 一、背景与问题

现有联机是**会话级 1v1 盲转**：托盘生成 6 位房间码 → 剪贴板发给好友 → 对方粘贴加入 → 两台机器互看桌宠状态。

三条硬限制让它长不成社交功能：

| 限制 | 后果 |
|---|---|
| **严格 1v1**（relay `room.peers.size >= 2` 即拒） | 三个人想一起待着做不到 |
| **会话级一次性**（关软件即散，房间码每次重开都变） | 熟人每次都要重新开房重发码，社交关系零积累 |
| **无发现机制**（房间码必须私下传递） | 只能约好的人进，陌生人无从加入；房间不存在「被看到」的可能 |

用户要的是**游戏联机房**那种概念：我开一个房，别人**从某个地方能看到它并选择加入**。房间是有社交属性的虚拟聚合单元，不是一个视觉场景。

## 二、产品决策（已与用户确认）

| 决策点 | 结论 |
|---|---|
| 房间形态 | **虚拟社交单元**，不是等距场景。房间 = 名字 + 类型 + 成员 + 聊天流，落在一个列表窗里 |
| 持久性 | **常驻房间**：固定 roomId，关了再开还是同一间；可收藏、可反复进出 |
| 发现机制 | **公共房间列表**（可浏览/按类型筛选/搜名字）；同时保留私密房（不上架，凭码进） |
| 房间类型 | 摸鱼房 / 自习室 / 夜猫房 / 联机房（开房时选，列表可筛） |
| 容量 | 4~12 人，默认 8 |
| 房内玩法 | **轻在场 + 打招呼**（成员列表 + 状态 + 挥手）。无成长线、无收集、无偷 |
| **聊天** | **房内文字聊天，能看到最近的记录**（用户明确要求；见 §五） |
| 游戏化 | 接入现有本地系统：房内在线也攒点数/箱子；不造第二套经济 |
| 身份 | 沿用皮肤市场范式：**本地昵称 + token**，零账号体系 |
| 后续挂载点 | 「多人合作促进开箱/作品数值」作为独立模块后置，本版只留接口，不实现 |

### 2.1 明确承担的风险

用户选择「轻在场 + 打招呼」，并已知悉这版**留存动力偏弱**（08-03 调研结论：单向炫耀留不住人）。决策理由：先用最小代价验证「公共房间」这个框架本身成立，合作玩法留给后续专门模块。

本 spec 因此把「验证框架成立」当第一目标，**留存指标不作为本版成败判据**（见 §九）。

## 三、总体架构

### 3.1 为什么必须是新服务，不能扩 relay

`relay/server.mjs` 的铁律写在文件头：**paired 之后不解析任何帧内容、不落盘**。这条铁律是现有联机隐私声明的全部依据（「不发就是最好的加密」）。

公共房间服务**必须解析帧**（房间列表、成员进出、聊天广播）并且**必须落盘**（常驻房间、聊天记录）。把它塞进 relay 等于亲手废掉 relay 的隐私声明。

因此：**新增独立 workspace `rooms/`**，与 `relay/`、`market/` 并列。

| 服务 | 端口 | 状态 | 职责 |
|---|---|---|---|
| `relay/` | 24250 | 零状态、盲转 | 1v1 好友 presence（**本版不动**） |
| `market/` | 24251 | 有状态、落盘 | 皮肤市场 |
| **`rooms/`** | **24252** | **有状态、落盘** | **公共房间：列表 / 成员 / 在场 / 聊天** |

沿用 `relay`/`market` 的部署约定：单文件 `server.mjs` + 唯一依赖 `ws`，**禁止 import 仓库其他模块**（可整目录 scp）；systemd `DynamicUser` 常驻；日志只记数量不记正文。

### 3.2 数据流

```
你的机器                          rooms 服务(24252)                别人的机器
状态机/agent/music ─┐
                    ├→ rooms.ts(main) ──WS──→ 房间注册表          ┌→ rooms.ts(main)
房间窗 renderer ────┘      ↑              成员表 / 在场表          │
  (列表/成员/聊天)         └──── 广播 ──── 聊天环形缓冲(50条) ─────┘
```

客户端新增一条 WS 长连接（与 relay 那条互不影响，可同时在线）。

### 3.3 客户端模块划分

| 文件 | 职责 |
|---|---|
| `app/src/main/rooms/rooms.ts` | 房间链路：连服务、开/加/退房、出在场帧、收广播 → 转发 renderer |
| `app/src/main/rooms/protocol.ts` | 帧类型定义 + **纯逻辑**校验（可单测） |
| `app/src/main/rooms/chat-rules.ts` | 聊天纯逻辑：长度/频率限制、本地去重、历史合并（可单测） |
| `app/src/renderer/lounge/` | **第 6 个 renderer**：房间列表 + 房内视图（成员/聊天） |

### 3.4 关键决策：成员用缩略图，不开替身窗

1v1 联机会为对端开一个 `?remote=1` 替身窗，并传 ~12MB 角色包。**12 人房不能这么做**：12 个桌面窗 + 132MB 传输，两条都不可接受。

所以公共房间的成员表现是**房间窗内的一行**：64px 角色缩略图（从 `source.png` 缩，约 5KB）+ 昵称 + 状态 + 当前动作名。

- 桌面替身窗**保留给 1v1 好友链接**（现有功能，不动）
- 「让房友的宠出现在我桌面上」后置，需要先解决按需/限量分发

## 四、房间模型与协议

### 4.1 房间数据

```ts
interface PublicRoom {
  roomId: string;        // 服务端生成，8 位（沿用 relay 去易混字符集），永久不变
  name: string;          // 房主起，≤24 字，服务端截断
  kind: RoomKind;        // 'idle' 摸鱼 | 'study' 自习 | 'night' 夜猫 | 'coop' 联机
  capacity: number;      // 4~12，默认 8
  listed: boolean;       // true 上公共列表；false 私密房（凭 roomId 进）
  ownerToken: string;    // 房主管理码（只存服务端，比对用）
  members: Member[];     // 常驻成员（进过就算，不是只有在线的）
  createdAt: number;
  lastActiveAt: number;  // 空房回收依据
}

interface Member {
  memberId: string;      // 客户端首次连接时服务端分配，存本地 Settings
  nickname: string;      // ≤16 字
  avatarHash?: string;   // 角色缩略图指纹（服务端缓存 64px PNG）
  joinedAt: number;
  lastSeenAt: number;
}

/** 在场状态（只在线成员有；不落盘，进程重启即空） */
interface Presence {
  memberId: string;
  mode: LinkMode;        // 复用现有：idle/thinking/working/waiting/done/error/music
  action?: string;       // 动作名提示
}
```

**为什么 members 存「进过的人」而不是「在线的人」**：常驻房间的社交资产就是这份名单——「这个房有 8 个常客」和「现在有 3 个人在线」是两件事，列表都要显示。

### 4.2 客户端 → 服务端

| 帧 | 内容 | 说明 |
|---|---|---|
| `hello` | `{memberId?, nickname, protoVer, avatarHash?}` | 连上就发；无 memberId 则服务端分配并回发 |
| `list` | `{kind?, q?}` | 拉房间列表（可按类型/关键词筛） |
| `create` | `{name, kind, capacity, listed}` | 开房 → 回 `room` 帧带 roomId + ownerToken |
| `join` | `{roomId}` | 加入 → 回 `joined` 带房间快照 + 最近聊天 |
| `leave` | `{roomId}` | 退房（区别于掉线） |
| `presence` | `{mode, action?}` | 在场状态，on-change + 30s 心跳 |
| `chat` | `{text}` | 发言，≤200 字 |
| `wave` | `{targetMemberId}` | 打招呼 |
| `room:update` | `{name?, kind?, listed?, token}` | 改房间设置（校验 ownerToken） |
| `room:kick` | `{memberId, token}` | 踢人（房主，校验 token） |

### 4.3 服务端 → 客户端

| 帧 | 内容 | 时机 |
|---|---|---|
| `hello:ack` | `{memberId, serverTime}` | 连接建立 |
| `rooms` | `{rooms: RoomBrief[]}` | 应答 `list`；`RoomBrief` = roomId/name/kind/在线数/容量/成员数 |
| `room` | `{roomId, ownerToken}` | 应答 `create` |
| `joined` | `{room: RoomSnapshot, chat: ChatMsg[]}` | 应答 `join`，**带最近 50 条聊天** |
| `member:in` \| `member:out` | `{roomId, member}` | 成员上下线（房内广播） |
| `presence` | `{roomId, memberId, mode, action?}` | 在场变化（房内广播） |
| `chat` | `{roomId, msg: ChatMsg}` | 新发言（房内广播） |
| `wave` | `{roomId, fromMemberId, fromNickname}` | 有人跟你打招呼 |
| `error` | `{code}` | `room_not_found` / `room_full` / `rate_limited` / `bad_frame` / `not_owner` / `banned` |

`protoVer` 不一致 → 提示升级并断开，不做兼容层（沿用 1v1 联机的版本策略）。

## 五、聊天与最近记录（用户明确要求）

### 5.1 「能看到最近的」= 服务端保留最近 50 条

```ts
interface ChatMsg {
  id: string;            // 服务端生成，单调递增（客户端去重/排序用）
  memberId: string;
  nickname: string;      // 快照存一份：改昵称不追溯改历史，也免客户端反查
  text: string;          // ≤200 字
  at: number;            // 服务端时间戳（不信客户端时钟）
}
```

每房一个**环形缓冲，只留最近 50 条**，随房间落盘。进房 `joined` 帧一次带回，之后靠 `chat` 广播增量。

**为什么是 50 条 / 为什么不做无限历史**：

- 50 条 ≈ 一屏多一点，够「刚才聊了什么」——这正是用户要的「最近的」
- 无限历史意味着分页 API、本地缓存同步、冷热存储，工程量数倍
- 更重要的是**责任边界**：完整聊天档案是一份长期个人数据资产，需要导出/删除/追溯能力（见 §5.3）。50 条滚动缓冲天然自我清理

### 5.2 频率与长度限制（服务端强制）

| 限制 | 值 | 理由 |
|---|---|---|
| 单条长度 | ≤200 字（服务端截断） | 房间不是长文场所 |
| 发言频率 | 3 秒 1 条，10 条/分钟 | 防刷屏；超限回 `rate_limited`，不断连 |
| 同内容连发 | 连续 3 条完全相同 → 拒 | 防复制粘贴刷屏 |
| 帧大小 | `maxPayload 32KB` | 房间帧全是小文本（沿用 relay 的显式上限做法） |

限制逻辑放 `chat-rules.ts` **纯函数**，客户端和服务端各调一次：客户端先挡（即时反馈），服务端权威（不信客户端）。

### 5.3 隐私与内容责任（本版最大的新增风险）

1v1 联机的隐私铁律是「敏感内容根本不发」。**聊天从根本上改变了这个前提**：用户主动输入的文字必须离开本机、经过服务端、落盘、广播给陌生人。这不是能靠「不发」规避的，只能靠明示和边界管理。

**因此本版必须做到**：

| 项 | 做法 |
|---|---|
| **首次入房明示** | 首次加入公共房间弹一次确认框：「公共房间的发言会发送到服务器并对房内所有人可见，也会保留最近 50 条供后来者查看。」不同意则不进 |
| **agent/会话内容严格隔离** | 聊天输入框是**唯一**的文字出口，只接用户手打的字。气泡正文 / `last_assistant_message` / transcript / cwd / persona **绝不允许**以任何形式（含「一键分享结论到房间」这类便利功能）流入聊天。这条要有测试守着 |
| **状态同步维持原粒度** | 房内 presence 仍然只发状态枚举 + 动作名，**不发**曲名（1v1 有 `linkShareSong` 开关是因为对端是好友；公共房间对象是陌生人，不给这个开关） |
| **自己的发言可撤回** | 房内可删自己的消息（服务端按 memberId 校验），删除后从缓冲移除并广播 |
| **举报与房主管理** | 每条消息可举报（服务端只记计数 + 消息快照，不做自动判定）；房主可踢人；被踢者该房 `banned` |
| **不做的事** | 不做私聊（1v1 是另一条链路的事）、不传图片/文件、不做 @提醒、不接入任何 LLM 生成内容 |

**运营侧的诚实说明**：这是自部署单机服务，没有 7×24 审核能力。所以公共房间列表**默认只展示，不推荐/不排行**，且首版建议**限制房间总数**（见 §八），把它当「熟人小圈子的公共入口」而非开放广场运营。若后续真的有陌生人规模，需要补审核与合规评估——这属于本 spec 范围外，届时必须单独立项。

### 5.4 客户端聊天体验

- 房内视图下半部是聊天流（气泡列表，自己的靠右），上半部是成员栏
- 新消息在房间窗未聚焦时：托盘图标角标 + 可选系统通知（默认关，避免打扰）
- **不复用桌宠气泡窗**：桌宠气泡是 agent 结论专用（固定 340×500 穿透窗，血泪坑 18），聊天塞进去会和 agent 语义打架

## 六、用户体验

### 6.1 入口

桌宠右键菜单新增「**公共房间**」（与现有「角色工作室」「小房间」并列），打开 lounge 窗。托盘「联机」菜单保持原样不动（那是 1v1 好友链接）。

两条链路的语义区分要在 UI 上说清：

| | 托盘「联机」 | 右键「公共房间」 |
|---|---|---|
| 对象 | 一个好友 | 一屋子人（含陌生人） |
| 表现 | 好友的宠出现在你桌面 | 房间窗里一行行成员 |
| 内容 | 只有状态 | 状态 + 文字聊天 |

### 6.2 lounge 窗两个视图

**房间列表**（未进房时）

```
┌─────────────────────────────────────────┐
│ 公共房间          [昵称: 阿蛋 ✎] [开房] │
│ 全部 | 摸鱼 | 自习 | 夜猫 | 联机  [搜索]│
├─────────────────────────────────────────┤
│ ★ 摸鱼小筑          摸鱼   3/8 在线  进 │  ← 收藏置顶
│   常客 8 人 · 刚刚有人说话                │
│   夜班修仙团        夜猫   1/12 在线 进 │
│   随便聊聊          摸鱼   0/8  在线 进 │  ← 空房也能进
└─────────────────────────────────────────┘
```

**房内**（已进房）

```
┌─────────────────────────────────────────┐
│ ← 摸鱼小筑 (3/8)         [设置] [退出]  │
├─────────────────────────────────────────┤
│ [头]阿蛋(你)  在敲代码   [头]小明 听歌中 │
│ [头]小红      摸鱼中 👋                  │
├─────────────────────────────────────────┤
│ 小明: 今天需求又变了                     │
│ 小红: 顶不住                             │
│                        今天也是摸鱼 :我  │
├─────────────────────────────────────────┤
│ [说点什么…                      ] [发送] │
└─────────────────────────────────────────┘
```

- 成员头像 = 64px 角色缩略图；点头像 → 挥手打招呼
- 收到别人挥手 → **自己桌宠播 `wave` 动作**（没有该动作则回退 `talk_happy`），房内该成员行冒 👋
- 状态文案由 mode 映射（`thinking`→「在思考」`working`→「在敲代码」`music`→「听歌中」`idle`→「摸鱼中」），**不显示具体项目/文件名**

### 6.3 房间窗形态

普通窗口（**不是**透明穿透窗），420×560，可缩放，独立于桌宠窗。理由：要输入文字、要滚动、要长时间停留，透明穿透窗全是负担（血泪坑 5/18 那套约束都是为贴纸窗服务的）。

关窗 = 退房（发 `leave`），不做后台挂机在房——避免「我以为退了其实还在房里说话被人看着」。

### 6.4 昵称

首次打开 lounge 若无昵称，引导设置。**复用 `Settings.marketNickname`**（皮肤市场已有），统一为 `Settings.nickname`，市场侧做兼容读取——同一个人在市场和房间应该是同一个名字。

## 七、游戏化接入（复用现有经济）

### 7.1 房内在线 = 挂机的一种

现有规则（`app/src/shared/furniture.ts` 的「玩法数值」段是唯一数据源）：挂机满 15 分钟 → 1 个箱子（`IDLE_MS_PER_BOX`）；敲键盘 1 点；agent 跑完一轮 10 点。

**本版只加一条**：在公共房间里在线的时间，照常计入挂机时长。

即：**不新增任何数值**。`progress.ts` 的 30s tick 和 `settleIdle` 完全不用改——房间在线的用户本来就在挂机。这条写进 spec 只是为了明确「进房不影响原有积累，也不额外加速」。

**为什么第一版不给房间专属奖励**：房内在线额外产出会立刻制造「挂房刷箱子」的最优策略，让房间沦为挂机农场，与「社交在场」的目标相反。合作产出留给后续模块，届时应该绑**互动行为**（一起做了什么）而不是**在线时长**。

### 7.2 房间装饰用现有家具（后置到 M3）

房主可用自己库存的家具装饰房间（房间窗顶部一条装饰带），复用 `shared/furniture.ts` 的品质分级和 `decor-pack.ts` 的贴纸资产。这是纯展示，不产出。

排在最后是因为它需要「房间装饰状态」这一份新的服务端数据 + 一套摆放 UI，而对验证「公共房间是否成立」没有贡献。

### 7.3 后续合作模块的挂载点（本版不实现）

用户明确要的后续方向：**多人在一起合作，促进开箱和作品制作相关的数值提升**。本版为它留三个接口，但不实现任何数值：

| 挂载点 | 本版做到哪一步 |
|---|---|
| 服务端能识别「谁和谁同时在房里多久」 | `Presence` 表已有 memberId + 时间，天然可算共处时长；本版不落盘不计算 |
| 客户端能收到「房间事件」并转成本地进度 | `rooms.ts` → `progress.ts` 的调用通道预留一个 `applyRoomReward(kind, amount)` 入口，本版无调用方 |
| 数值定义位置 | 新数值一律进 `shared/furniture.ts` 的「玩法数值」段，与现有常量并列（禁止在 rooms 模块里另立数值） |

设计约束先写下来，免得后续走偏：合作奖励必须**绑互动、不绑在线时长**；必须**有每日上限**（防挂机农场）；**不引入负向机制**（不偷不抢，与 08-03 的软偷是不同模块，若两者都做需要重新权衡力度）。

## 八、服务端实现与运维

### 8.1 落盘

单文件 JSON（`/var/lib/qbot-rooms/rooms.json`），全量内存 + 定时落盘（30s 脏写）+ 退出前 flush。

理由：房间数上限 200、每房 12 成员 + 50 条聊天 → 最坏约 200×(12×100B + 50×300B) ≈ 3.3MB。这个量级不值得上数据库。

### 8.2 容量与回收

| 项 | 值 | 理由 |
|---|---|---|
| 房间总数上限 | **200** | 小 VPS 承载 + §5.3 的运营边界（当熟人圈入口，不当开放广场） |
| 单房容量 | 4~12 | 产品决策 |
| 单连接可建房数 | 3 | 防一人刷满列表 |
| 空房回收 | **7 天无人进 → 删** | 常驻的前提是别被无限累积撑爆；7 天够覆盖「周末不上线」 |
| 单人房不特殊处理 | — | 与 relay 不同：常驻房间空着是正常状态，不该像 1v1 那样 10min TTL 解散 |
| 心跳 | 30s ping，2 次不回 terminate | 沿用 relay 做法 |

### 8.3 缩略图

`avatarHash` 对应一张 64px PNG（约 5KB），首次上报时随 `hello` 带上（base64），服务端按 hash 缓存，之后同 hash 直接复用。总量上限：200 房 × 12 人 × 5KB ≈ 12MB，加个 LRU 上限 2000 张即可。

### 8.4 日志与隐私

**日志只记数量**（房间数/连接数/消息条数），沿用 relay/market 的做法。**聊天正文绝不进日志**——正文已经落盘在 rooms.json 里（这是功能必需），再进日志只是多一份泄漏面。

### 8.5 传输安全（明确的已知缺口）

首版明文 WS，与 relay 现状一致。但**公共房间的暴露面比 1v1 大**：1v1 传的是状态枚举（抓包也看不出什么），公共房间传的是用户手打的聊天正文。

所以：**wss 在本 spec 里不是「后置项」，而是上线前的必要项**（Caddy 反代 + Let's Encrypt，与 market 可共用）。这条与 §5.3 的首次入房明示一起，构成聊天功能的最低安全门槛。

若上线时 wss 未就绪，则首次入房明示必须额外写明「当前传输未加密」。

## 十、否决项与后置项

**本版不做**：

- ❌ 房友的宠出现在你桌面（12×12MB 资产分发不可行；需要先做按需/限量分发）
- ❌ 私聊（1v1 链路的事，别在房间里造第二套）
- ❌ 图片/文件传输、@提醒、表情包
- ❌ 房间成长线 / 房经验 / 房等级（用户明确本版不要）
- ❌ 房间花园 / 偷取（08-03 的软偷是独立模块，与合作模块的力度需一起权衡）
- ❌ 房间排行榜 / 热度推荐（违背 08-03「不做数值排行榜」，也会放大 §5.3 的运营责任）
- ❌ 语音（叽歪语音是本地程序化合成，与真人语音是完全不同的事）
- ❌ 账号体系 / 登录（沿用昵称+token）

**后置**：

- 房间装饰（§7.2，排到 M3 之后）
- 合作产出模块（§7.3，用户已明确要做，但需单独设计数值）
- 房主转让、房间公告、成员备注
- 移动端 / Web 端看房（需要服务端补 HTTP 接口）

## 十一、未定，需要一起定

1. **陌生人还是熟人**——本 spec 按「熟人小圈子的公共入口」设计（房间数 200 上限、不做推荐排行）。如果目标是真正的陌生人开放广场，那么内容审核、举报处置流程、合规评估都必须先立项，工程量和责任量级完全不同。这个定位问题决定后面所有取舍，**建议在 M0 开工前明确**。

2. **昵称唯一性**——当前设计允许重名（两个「阿蛋」）。要不要加 4 位后缀区分（同 agent 气泡的同名来源处理）？重名在聊天里比在气泡里更容易混淆。

3. **房主不在时房间谁管**——常驻房间的房主可能长期不上线，此时无人能踢人。选项：房主可指定副手 / 房内投票踢人 / 不处理（房主不在就没人管）。本 spec 暂按「不处理」，但这在有陌生人时会变成问题（与第 1 条联动）。

4. **聊天历史 50 条是否够**——用户要求「能看到最近的」，50 条是我的取值。如果实际用起来觉得短，扩到 200 条的代价可控（约 3.3MB → 13MB）；但无限历史是另一回事（见 §5.1）。

5. **wss 时间表**——§8.5 把 wss 列为上线必要项。需要确认 VPS 上是否已有可复用的域名和证书（现有 nginx 占着 80/443 跑别的站点），否则要先解决反代共存。
