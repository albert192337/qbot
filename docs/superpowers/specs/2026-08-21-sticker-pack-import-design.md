# QBot 表情包导入：贴纸资源 → 动作映射

> 版本：v0.2（2026-08-21）· 评审后修订
> 状态：草稿（核心决策已定，模型型号待烟测）
> 上游：CLAUDE.md、`2026-08-16-product-features-and-actions-redesign.md`（动作体系重构）

---

## 一、背景与目标

### 1.1 现状

QBot 的角色动作来源只有一条路：

```
丢一张角色图 → 生成三视图 → 逐动作生成（首帧→视频→抠像→转码）→ 资产包
```

- 每生成一个动作 ≈ **5-8 分钟 + API 费用**（首帧 1-2min + 视频 3-5min + 抠像 1min）；
- 一只 S 档角色全量动作要 **30-50 分钟 + 数元 API 费**；
- 用户没有「现有素材直接拿来用」的入口。

### 1.2 需求

支持**直接导入一套表情包资源**（大概率是 GIF 格式），绕过三视图/逐动作生成管线：

1. 用户导入一套 GIF 表情包；
2. 系统对每张 GIF 做**粗略分析打标**（模型识别它「像什么动作」）；
3. 打标结果**映射到固定动作槽位**（idle/sleep/tea/…）；
4. 映射可人工复核修正；
5. 确认后 GIF 直接成为桌宠的可用动作，状态机照常调度。

### 1.3 目标与边界

| 目标 | 非目标 |
|---|---|
| GIF 表情包一键导入 | 表情包生成/编辑 |
| 模型粗标 + 人工复核的映射闭环 | 精确动作识别（不需要语义级准确） |
| 导入动作与现有状态机无缝衔接 | 替换三视图生成管线（两套并存） |
| 资产包内可追溯、可回退 | 服务端表情包市场 |

## 二、用户流程（产品视角）

### 2.1 主流程

```
[Studio · 动作配置] "导入表情包" 按钮
        │
        ▼
① 选包：选择本地文件夹（支持多选 GIF，或拖入）
        │
        ▼
② 模型打标（数秒）：每张 GIF → 建议槽位 + 置信度
        │
        ▼
③ 复核界面：网格展示所有 GIF，每张带「建议槽位 + 置信度徽标」
   - 高置信（≥0.6）：绿色，一键全收
   - 中置信（0.35~0.6）：黄色，提示人工确认
   - 低置信（<0.35）：红色，强制人工指定
   - 槽位下拉可改；无主贴纸进「备选库」
        │
        ▼
④ 确认应用：转码 → 落盘 → manifest 更新 → 桌宠热重载
```

### 2.2 复核界面的交互细节

- 每个动作槽位一行，显示当前贴纸缩略图（抽帧动画预览）+ 贴纸文件名；
- 同一槽位被多张贴纸建议时，按置信度排序，默认取最高，其余进备选库（备选库可随时换）；
- 贴纸数 < 槽位数：缺的槽位保持原生成动作（**混合模式**，见 §4.3）；
- 贴纸数 > 槽位数：多余的进备选库；
- 复核阶段不落盘，取消 = 什么都没发生。

### 2.3 入口

- 主入口：Studio「动作配置」tab 新增「导入表情包」；
- 桌宠右键菜单「角色工作室」内同一入口。

### 2.4 一次成功后的反馈

- 桌宠立刻播放新动作（热重载）；
- 气泡提示「已导入 N 个表情动作，槽位 X/Y/Z 已替换，备选库 M 个」。

## 三、动作槽位设计（映射目标）

### 3.1 固定槽位

导入的贴纸要落到哪个槽位，由「贴纸语义」决定。语义来自现有动作体系（§3.1 基础动作 + 第二层场景动作）：

| 槽位 | 贴纸语义（模型打标目标） | 状态机用途 | 生成动作 |
|---|---|---|---|
| `idle` | 安静待机/呼吸/眨眼 | 常驻循环 | 基础 6 动作 |
| `sleep` | 睡觉/瘫倒/闭眼 | done 庆祝、深夜 | 基础 6 动作 |
| `tea` | 悠闲/喝茶/放空 | agent thinking/working、meeting 默认 | 基础 6 动作 |
| `talk_happy` | 开心/欢呼/雀跃 | music 默认、auto 随机 | 基础 6 动作 |
| `talk_annoyed` | 不耐烦/生气/催促 | agent waiting/error | 基础 6 动作 |
| `celebrate` | 庆祝/撒花/转圈 | 未来 done（动作体系重构 §2.1） | S+ 场景动作 |
| `focus` | 专注/敲键盘/写东西 | 未来 agent working（重构后） | S+ 场景动作 |
| `wave` | 打招呼/挥手 | 未来早安 | S+ 场景动作 |

**v1 只打标前 5 个基础槽位**；celebrate/focus/wave 作为模型可输出但暂不落槽的类别（进备选库），等动作体系重构落地后自动启用。这样导入功能不依赖重构，先跑通闭环。

### 3.2 语义 → 槽位映射表（模型输出约束）

模型输出的打标类别（枚举），与槽位一一对应：

| 类别 | 判定依据（提示词内给出） | 示例贴纸 |
|---|---|---|
| `idle` | 静止、轻微呼吸、眨眼、无强烈情绪 | 猫咪眨眼 |
| `sleep` | 闭眼、ZZZ、瘫倒、趴着 | 睡觉的柴犬 |
| `tea` | 悠闲、喝茶、放空、慢节奏晃动 | 喝茶的熊猫 |
| `happy` | 开心、兴奋、蹦跳、转圈、撒花 | 欢呼的小黄鸭 |
| `annoyed` | 生气、不耐烦、叹气、翻白眼 | 生气的猫猫 |
| `celebrate` | 庆祝、比耶、礼花（v1 进备选库） | 干杯 |
| `focus` | 专注、写字、敲键盘、看书 | 认真工作 |
| `wave` | 打招呼、挥手（v1 进备选库） | 你好 |
| `other` | 以上都不像（进备选库） | 哭泣、震惊 |

**关键设计：模型不输出"动作 ID"，输出"语义类别"**。理由：
1. 贴纸是任意素材，用户期望的是「它表达什么情绪/状态」，不是「它叫 tea」；
2. 语义类别比动作 ID 更稳定，动作体系重构后映射表不变；
3. 类别数少（9 个），模型粗标准确率更高，用户也更好理解。

## 四、数据与技术设计

### 4.1 资产落盘

沿用角色包目录，不新建数据区：

```
characters/<dirId>/
├── manifest.json          # 新增 importedActions 字段（§4.2）
└── imported/
    ├── idle.webm          # 转码后（GIF→webm，含 alpha）
    ├── sleep.webm
    └── _raw/
        ├── idle.gif       # 原始贴纸永久保留（改映射零成本重转码）
        └── 原始文件名.png # 抽帧参考（复核界面预览用）
```

### 4.2 manifest 扩展

```ts
/** manifest.json 新增字段（可选，缺省 = 无导入） */
interface ManifestImportedAction {
  /** 转码产物（相对角色包根） */
  webm: string;
  /** 原始贴纸（相对角色包根，改映射时重转码的输入） */
  raw: string;
  /** 导入时的模型建议槽位（追溯用） */
  suggestedSlot?: string;
  /** 导入时的置信度 [0,1] */
  confidence?: number;
  /** 用户是否人工改过槽位 */
  manualOverride?: boolean;
  /** 贴纸原始文件名（复核界面/调试显示） */
  sourceName: string;
}

interface Manifest {
  // ...现有字段
  /** 贴纸导入动作：key = 槽位（PlayableId）。缺省 = 未导入 */
  importedActions?: Record<string, ManifestImportedAction>;
}
```

**为什么新增字段而不是覆盖 `actions`**：
1. 可回退——删除 `importedActions` 即恢复生成动作，原始 webm 不动；
2. 混合模式（§4.3）需要知道哪些槽位是导入的；
3. 追溯——`suggestedSlot/confidence/manualOverride` 是复核体验的审计信息。

### 4.3 播放优先级（混合模式）

Player 加载时合并：`importedActions` 覆盖同名标准动作，其余槽位用生成动作：

```
manifest.actions（标准 6 个，生成产物）
  ⊕ manifest.importedActions（导入贴纸，覆盖同名 key）
  ⊕ manifest.customActions（自定义动作，已有逻辑）
```

```
available = {标准动作中未被打标的} ∪ {importedActions 的 key} ∪ {customActions 的 key}
```

状态机**零改动**——它只认 `PlayableId`，播放层解析哪个文件是它的事。

### 4.4 转码

GIF → webm（VP9 + alpha），**不做抠像、不做归一化**：

- GIF 自带 alpha，无需 chroma key；
- 不归一化意味着保持贴纸原始画幅与内容（贴纸是成品，不是角色动作图）；
- 走 ffmpeg-static，复用现有 `chroma.ts` 的 `toWebm` 基建（新增 `gifToWebm()` 路径，不经绿幕采样/漂移检查）；
- 循环靠 GIF 本身的帧结构（转码时 `-loop 0`），不依赖生成层。

**画幅注意**：桌宠窗是方形（宽=高，`video { width:100% }`），非方形贴纸（如横条 banner 型）会变形/过小。**已定：方案 B——方形画布居中贴纸，透明 padding**：
- 转码时 `-vf "scale=...:...,pad=...:...:(ow-iw)/2:(oh-ih)/2"` 到统一方形，桌宠窗逻辑零改动（不触碰透明窗 resize 血泪坑 18）；
- 复核界面提示「横版贴纸会自动居中到方形画布」；
- 方案 A（CSS `object-fit: contain` + 动态调窗尺寸）已否决：透明窗 resize 有渲染 bug。

### 4.5 模型打标

**能力需求**：看懂贴纸内容（画面主体/情绪/动作倾向）。

**输入**：每张 GIF 抽 3 帧（首/中/尾）转 data URL，批量进一次请求（避免逐张请求的延迟与费用；一批 10~20 张为上限，多了分批）。

**输出**：每张贴纸 → `{ category, confidence, reason }`（reason 一句话，复核界面展示帮助用户理解模型判断）。

**端点**：Ark 新增 `chat/completions` 轻量客户端（现在 `ark.ts` 只有生图/生视频，没有文本/视觉理解能力）。**已定：模型用 `doubao-seed-2-0-mini`**（低延迟 + 高并发 + 最低成本，输入 ¥0.2/M、输出 ¥2/M；单批 50 张约 ¥0.009）；模型名走 `PipelineConfig` 新增 `visionModel` 字段，默认 `doubao-seed-2-0-mini-260428`（或最新版本号）。图片精度用 `low` 档（打标够用且省 tokens）。

**提示词要点**：
- 只输出 JSON 数组（一次解析）；
- 类别枚举 + 每个类别的判定依据（§3.2 表）直接进提示词；
- few-shot 示例 3~4 个（典型贴纸 → 正确类别）；
- 「宁 low 勿错」：不确定就给低置信度，让用户兜底。

**置信度阈值**（复核界面三色徽标）：
- ≥0.6 绿色 · 自动采纳；
- 0.35~0.6 黄色 · 建议保留待人工确认；
- <0.35 红色 · 强制人工指定。

### 4.6 失败与异常

| 场景 | 处理 |
|---|---|
| 模型返回非 JSON / 类别非法 | 该贴纸降级为 `other`（进备选库），其余继续 |
| API 失败（网络/超时） | 整体中止，界面报错，不落任何盘 |
| 单张 GIF 损坏/无法解码 | 跳过并在复核界面标红提示 |
| 同一槽位多张贴纸竞争 | 取最高置信度，其余进备选库 |
| 贴纸数不足 5 个 | 缺槽位保持生成动作（混合模式） |
| 导入后想反悔 | 删除 `importedActions` 恢复生成动作（一步回退） |
| 贴纸画幅比例悬殊 | 转码统一方形画布（§4.4 方案 B） |

### 4.7 模块划分

| 模块 | 职责 | 归属 |
|---|---|---|
| `sticker-import.ts`（pipeline） | GIF 抽帧、批量打标（调 Ark vision）、JSON 解析、`gifToWebm` 转码、落盘；**纯逻辑可单测** | pipeline（零 Electron 依赖，遵守约定） |
| `sticker-importer.ts`（main） | IPC 入口、manifest 读写、热重载广播（复用 `broadcastCharacterActivated`） | app main |
| Studio「表情包导入」tab | 选包、复核网格、确认/取消 | app renderer |

## 五、与现有体系的关系

### 5.1 与动作体系重构（2026-08-16 spec）的衔接

- 重构后动作分三层：基础 6 + 场景 4（focus/wave/yawn/celebrate）+ 情绪变体；
- 本设计 v1 只落基础 5 个槽位；celebrate/focus/wave 已进打标类别但暂不落槽；
- 重构落地后，`importedActions` 的 key 直接新增这些槽位即可，**映射表、播放层、数据模型都不用动**。

### 5.2 与自定义动作（customActions）的区别

| | 自定义动作（已有） | 贴纸导入（本设计） |
|---|---|---|
| 来源 | 文本 prompt → 模型生成（花钱、耗时） | 用户现成 GIF（免费、秒级） |
| 语义 | 任意命名 | 固定槽位语义（表 3.1） |
| 播放 | 手动/联动可选 | 自动进入状态机调度 |
| 格式 | webm+gif（绿幕抠像） | webm（原生 alpha） |

两者互补：customActions 是「加一个动作」，贴纸导入是「换一套动作」。

## 七、已定决策与待确认事项

### 已定（2026-08-21 评审）

| 决策点 | 结论 |
|---|---|
| 打标模型 | **doubao-seed-2-0-mini**（低延迟 + 高并发 + 最低成本：输入 ¥0.2/M、输出 ¥2/M），走 Ark chat/completions；`visionModel` 可配置，默认 `doubao-seed-2-0-mini-260428` |
| 图片精度 | **low 档**（打标够用且省 tokens；Mini 支持 low/high/xhigh 三档） |
| 批次上限 | **≤50 张/批次**（防打标分批过载、复核网格不爆） |
| 格式支持 | **v1 只做 GIF**（APNG/WebP 留扩展位） |
| 替换 vs 并存 | **v1 只做替换槽位**：贴纸覆盖生成动作，删除 `importedActions` 一步回退；并存切换（每槽位生成/贴纸两套）留到后续 |
| 画幅策略 | **方案 B：方形画布居中 + 透明 padding**（方案 A 因透明窗 resize 渲染 bug 否决） |

### 待确认

目前无待确认事项（核心决策已全部定稿）。

## 八、一句话总结

**导入一套 GIF 表情包 → 模型按固定语义类别粗标（9 类、附置信度）→ 用户复核修正 → 转码成带 alpha 的 webm → 按槽位覆盖进 manifest → 状态机零改动直接调度；原始贴纸永久保留，删字段一步回退。**

## 九、真实环境实测记录（2026-08-22）

用真实贴纸包（线条小狗 447 张）+ 真实 API（doubao-seed-2-0-mini-260428）验证：

| 项 | 结果 |
|---|---|
| 型号可用性 | ✓ `doubao-seed-2-0-mini-260428` 真实可用，46 字符 key 正常计费 |
| 单批费用 | 50 张打标（4 次请求）≈ 分币级；耗时 ~1 分 40 秒（GIF 解码 + ffmpeg 抽帧占大头，API 本身 ~25s） |
| 类别识别质量 | ✓ 睡眠/喝茶/专注/得瑟/生气/无聊全部认对；`睡觉.gif`→sleep、`无聊、惬意.gif`→idle |
| **confidence 校准** | ✗ **模型天然过自信**：50 张里 49 张 ≥0.6（high）。prompt 明确分档措辞无效——小模型视觉分类的固有倾向。**不阻塞**：类别判断可靠，复核界面把置信度当辅助信号（同槽位竞争排序），三色仅作提示 |
| 50 张上限 | ✓ 255 张目录直接拒绝并报「请分批」（设计生效） |
| 抽帧性能 | 初版每帧一次 ffmpeg（150 次调用）→ 改为单次调用 `select` 多帧 + `image2pipe` + 5 路并发；仍 ~1:40（GIF 解码本身为主，可接受） |
| 落盘产物 | 640×640 VP9 + ALPHA_MODE:1，横版 padding 实测 alpha=0（真透明） |
| 完整闭环 | 打标 → 复核 → 转码 → manifest 合并 → 原 actions 一字未动 → 可回退 |

### 实测暴露的待办（后续版本）

1. **confidence 若要坚持三色分级**，需要换策略：或换更大模型（贵）、或在客户端做确定性修正（如按类别歧义度重映射）、或干脆去掉红黄档只留提示
2. 抽帧 `countGifFrames` 每张仍多一次 ffmpeg 探测（50 张 = 50 次），GIF 帧数其实可从 `-i` 探测结果一次拿全，后续可合并
