# 菠萝农场后续数值开发计划

日期：2026-09-22。状态：开发建议草案，未批准的参数不得当作正式规则。

依据：[原版规则与数值参考](./2026-09-21-pineapple-farm-original-rules-reference.md)及当前工作区代码。本次只规划，不补充外部考据，不改玩法代码或正式存档。原参考中 9 月 24 日、9 月 28 日内容仍按未来版本处理。

## 1. 开发方向

先建立可承载原版规则的结构，再填入已核实的机制与数值。顺序为：规则配置 → 三槽因子与果实数据 → 生长和天气 → 等级与亲和 → 繁育 → 经济校准。

明确区分三种数据用途：

- 原版参考：保留 A/B/U/?、来源、版本、生效时间；未知为 null。名称有证据，不代表概率或槽位归属有证据。
- 当前 QBot：现有线上/本地玩法的兼容基线，不能自动成为原版缺失项的默认值。
- 隔离试验：为验证代码完整性使用的人工参数，显式标记测试用途；不进入正式经济。

三槽名称按已明确需求采用果实、果皮、挂饰。槽位容量、覆盖规则、因子品质、果实品质算法仍分别待定；三槽不等于最多三个因子。

## 2. 当前代码与目标之间的差异

| 模块 | 当前工作区实现 | 下一步处理 |
|---|---|---|

| 品质 | 六档 Tier，tier() 取最高词条档位；种子货架另用物种 rarity | 分开记录种子、因子、果实和天气品质，原版判定待核实 |

| 等级 | 每 40 经验一级、最高 3 级；领取新图鉴项时每项加 20 经验 | 拆分农场等级、物种图鉴等级、种子等级及相互关系 |

注意：已有多处未提交改动，执行时应基于当时工作区重新核对，避免覆盖其他任务成果。

## 3. 分阶段交付

### P0：规则表与计算底座

交付：规则数据字典、配置校验器、旧规则基线、待核实清单。

- 每条参数带单位、适用条件、来源性质、证据级别、版本和生效时间。
- 分离存档结构版本与规则版本；一次结算明确使用哪个规则版本。
- 概率注明是独立触发率、条件概率还是抽签权重；不混用百分比与权重。
- null 表示缺资料，0 表示明确禁止或零概率；不得通过默认值把两者混为一谈。
- 只阻止缺少必需参数的相关机制运行，不让未完成的银行规则阻塞三槽预览。
- 把时间、随机数作为计算输入，支持固定随机种子重放和逐步结算记录。

验收：缺项能指出具体字段；条件概率及权重校验符合各自含义；现有规则配置化前后相同输入输出一致；试验配置无法被正式入口误加载。

### P1：三槽因子与果实实体

交付：可存取、展示、组合的果实数据及草莓隔离预览。

- 因子使用稳定 ID；名称、品质、槽位归属、适用物种、来源和视觉资源独立记录。
- 果实、果皮、挂饰支持分别查询；容量、互斥、覆盖优先级由明确策略决定，未知时不自动决定。
- 体型因子、实际重量、渲染缩放分开；不凭“巨大化”名称硬推重量倍率或售价。
- 种子亲和/遗传信息与果实已经获得的因子分开，避免把“更容易出现”实现成“必定携带”。
- 无法核实归属的旧词条保留为 legacy 数据，不删掉、不强行塞槽。
- 果实保存产生时的规则版本与结算结果；是否影响在地作物、旧种子另列版本政策。

验收：保存重读不丢因子；三个槽位分别展示；冲突测试给出确定结果；旧档副本的数量、重量、价格和词条不变。64 种草莓组合仅作视觉测试集合。

### P2：生长与天气结算

交付：隔离环境的“播种 → 生长 → 天气影响 → 收获”完整流程及计算明细。

- 把生长时长、重复采摘、可受天气影响的阶段、判定时点做成明确规则。
- 分开配置天气品质与天气名称、天气出现方式、持续时长、作物变异率、具体因子获得方式。
- 原版条件未核实前只支持测试情景，不填齐十个臆造名称、不猜三档品质名。
- 支持独立触发或分层抽取等不同明确策略，不预设所有天气都必须走同一三层概率树。
- 肥料、音乐、等级、亲和、社交等修正逐项标明作用对象与计算顺序；保底单列。
- 事件 ID 与处理记录保证重复刷新、重启或收获边界不重复抽奖。离线、跨日、时钟回拨和版本切换单独测试。

验收：同一事件不可刷取；显示的计算明细与实际结算一致；统计同时输出基础触发、保底触发及最终获得率。

### P3：等级、图鉴与亲和

交付：经验来源、等级门槛、解锁表及生效范围。

- 三种等级分别存储；是否联动由核实规则决定，不用一个 level 字段混装。
- 明确经验发生于播种、成熟、收获或发现的哪一步；奖励领取与经验增长是否绑定需证据。
- 亲和因子分别配置解锁条件与概率作用方式。
- 测试升级前后，旧种子、在地作物、新种子各自采用何种规则。

验收：同一事件经验只入账一次；门槛边界、最高级与旧档转换可验证；未解锁因子不能通过其他入口绕过限制。

### P4：繁育、杂交与培育

交付：先做本地规则模拟，再考虑跨玩家申请流程。

- 三类操作分别定义，不把松土、培育、杂交合并。
- 每种操作明确参与对象、成熟要求、亲本消耗、主动/被动次数、刷新周期、费用、产物。
- 遗传按已核实算法处理共有/单方因子、槽位冲突、品质变化及亲和；未知算法保持未启用。
- 本地提交要求扣除、次数占用、生成产物在同一事务中完成，重试不会重复产出。
- 跨玩家玩法另需权威结算与双方确认设计，不能仅交换客户端随机结果；不作为本轮底座的前置条件。

验收：相同亲本、重复请求、取消、失败恢复、次数刷新和槽位竞争均有确定结果。

### P5：经济仿真与参数定稿

交付：可重放的仿真报告与参数版本差异表；无需先制作完整数值后台。

- 输入种子/肥料成本、种植时长、获得率、重量分布、计价规则、土地数量、收购需求、已存在的旅行等消费。
- 分别模拟短时上线、常驻在线、离线种植、成熟留田、即时收获、偏重繁育等行为。
- 报告单位地块小时净收益、首次稀有因子所需次数/时间、7/30 天资产、升级时间、肥料回本率、留田机会成本。
- 同时看中位数和 P90/P99，防止低概率高倍率组合掩盖在平均数中。
- 抽样量按稀有事件概率与误差目标选择，报告置信区间；极低概率项使用边界/精确计算辅助，不能凭小样本零命中认定概率为零。
- 鉴定、银行、太阳花及活动修正待各自规则核实后扩展；当前不编造公式。

验收：原版复刻项验证是否符合证据与规则；若用户后续选择 QBot 自有平衡，再另定体验目标和参数，不为平衡效果暗改“原版”配置。

## 4. 下一轮建议执行范围

首批实施 P0 + P1 最小闭环：

1. 提取当前规则基线，建立独立参考/试验配置及校验。
2. 建立因子目录、三槽数据、独立品质字段和规则版本。
3. 用草莓隔离试验接通“测试配置 → 果实数据 → 三槽预览 → 保存重读”。
4. 提供一份可查看的计算记录，标出测试参数与缺失项。
5. 提供旧档副本迁移报告及基础回归结果。

这批完成即可验证结构能否承载后续规则，无需等待所有原版概率到齐。暂不把试验参数接到正式花园收益。

建议代码边界：共享层新增配置/因子契约；主进程花园模块承担校验与结算；预览只消费展示数据。纯规则继续保持可独立测试；具体拆文件按实施时依赖确定。

## 5. 原版资料补齐优先级

| 优先级 | 必需资料 | 阻塞什么 |
|---|---|---|
| 1 | 因子图鉴、三槽归属/容量、四类品质的定义 | 正式因子目录、覆盖规则和品质计算 |
| 2 | 全部天气、品质分类、概率含义、时点与持续时间 | 天气正式概率与结算策略 |
| 3 | 图鉴/种子/农场等级页、经验门槛与亲和说明 | 长期成长和因子解锁 |
| 4 | 杂交/培育对象、消耗、次数、遗传说明 | 可投入正式经济的繁育 |
| 5 | 重量/体型、售价、收购、银行和鉴定公式 | 完整经济闭环 |

对缺资料采用“相关正式机制待配置”，其余开发继续。后续若改为借鉴原版、自定数值，应单独建立项目设计表并明确批准范围。
