# 3D 房间与 Spine 家具交互调研

日期：2026-09-29。范围：研究与方案比较；未修改房间实现、依赖、素材或运行中的客户端。

## 结论

建议下一步验证 Electron + Three.js 的真实 3D 房间、独立家具模型、2D Spine 角色。自由摆放、多层房间和镜头切换不要求换 Godot。决定质感的主要因素是家具几何、材质、接触阴影、镜头、拖动反馈，以及角色与家具的空间关系。

先验证一张沙发与一个角色的完整交互，再扩大家具库。原来的透明家具图片可以作为设计参考和缩略图，不能直接成为可任意旋转的完整模型。

## 小人如何坐在沙发上

以下是我们可采用的设计，不是对鹰角内部代码的断言。

核心是“坐姿动画 + 家具上的座位标记 + 正确遮挡”。无需先做完整人体物理模拟，但站立素材直接下移也无法得到自然坐姿。

1. **家具定义座位。** 沙发模型记录左右座位的局部坐标、坐面高度、朝向，以及角色走近和离开的地点。移动、旋转沙发时，这些标记一起变换。
2. **角色有匹配动作。** 至少需要坐姿循环；进一步添加走近、坐下、起身。不同角色用骨盆或稳定根节点对齐座位，不能每帧按透明图边界重新缩放。
3. **动作与座位占用联动。** 预约空位 → 走近 → 对齐 → 坐下 → 坐姿循环 → 起身 → 释放。多人时由服务端确认占用，避免两人占同一位置。
4. **处理前后关系。** 靠背位于身体后方，近处扶手、茶几可遮住部分身体。先测试正常深度缓冲；若平面角色与立体家具穿插，再评估角色深度修正或分段渲染。不要用“角色永远画最上面”掩盖问题。
5. **补足接触感。** 坐面接触阴影、正确的腿部高度、轻微待机动作和一致色调。先把这些调好，再决定是否需要骨骼约束或额外物理效果。

受限镜头下，校准好的坐姿循环已经能很有效。若要绕到背后、从高处俯视，角色就需要更多方向素材，或改成 3D 角色；换引擎不会自动生成这些画面。

## 家具如何制作和拆分

这是拟议的项目规范，尚未批准或实现。

| 内容 | 建议交付与规则 |
| --- | --- |
| 房间外壳 | 地板、背墙、侧墙、天花板独立；支持剖面隐藏 |
| 单件家具 | 独立 GLB；统一世界单位、正面方向、地面原点；导出前应用缩放 |
| 材质 | 统一手绘或风格化路线；木材、布料通过颜色、粗糙度与细节区分 |
| 放置规则 | 落地、挂墙、天花板、桌面四类；各自有允许摆放的表面 |
| 占地 | 简化占地轮廓、碰撞体、可行走边界，与外观模型分离 |
| 互动点 | 座位、坐面朝向、走近点、离开点；灯具另有发光和光源标记 |
| 可替换部件 | 用户能单独换的抱枕、坐垫、桌饰才拆成独立组件 |
| 图集 | 同主题可共享贴图；模型仍须可独立选择、移动和保存 |
| 缩略图 | 从同一模型固定机位生成，避免列表与实物不一致 |

沙发整体作为一个家具对象，内部保留靠背、坐垫、扶手的命名节点，便于材质替换和必要的遮挡调整。没有必要把每根桌腿变成独立可操作家具。

制作流程：概念图 → 低复杂度模型验证尺寸和镜头 → 确定座位与占地 → 完善模型和贴图 → 导出 GLB → 在房间中检查拖动、坐姿和各个允许视角。生成图片可以帮助设计外观，仍需要制作并校验真实 3D 资产。

Three.js 已有 [GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html) 支持加载 glTF/GLB。该格式有助于保持资产独立于房间渲染实现。

## 自由摆放、多层房间与镜头

建议取消“全屋只有七个固定位置”的限制。地面家具拖动时通过屏幕射线求地面交点；挂画投到墙面；桌饰投到桌面。允许网格吸附与旋转，检测越界和占地冲突，提交前显示预览。拾起时轻微抬高，影子仍落在承托面，落下时短暂回弹。

这些是交互设计工作。Three.js 的 [Raycaster](https://threejs.org/docs/pages/Raycaster.html) 提供拾取基础，[OrbitControls](https://threejs.org/docs/pages/OrbitControls.html) 提供镜头旋转、平移、缩放及角度限制。

多层房间可组织成同一场景中的多个房间组，各自具有楼层位置、家具、角色和存档。总览展示楼层剖面，点选后镜头进入对应房间；非当前房间降低更新频率，屏幕外房间停止绘制。优先共享一个渲染器，不为每间屋重新创建一个 WebGL 上下文。

跨玩家房间展示还需要独立的房间布局同步、权限、在线状态与座位占用逻辑。3D 只负责视觉，不会替代这些联机功能。

建议先采用三个镜头状态：楼层总览、近正面生活视角、稍俯视布置视角；允许有限左右转动。具体角度由样板验证。任意 360° 应作为独立需求评估，因为它直接改变角色与家具资产的制作范围。

## 是否换 Godot

| 维度 | Electron + Three.js | Godot |
| --- | --- | --- |
| 当前项目接入 | 延用现有桌面窗口、界面、通信与数据 | 需要明确独立程序还是嵌入式运行，并验证桌面集成 |
| 3D 房间与家具 | 足以实现；编辑、交互工具需自行组织 | 适合通过完整场景编辑器组织内容 |
| Spine | 官方 spine-threejs 可把骨骼几何放入 3D 场景 | 官方已有 SpineSprite3D，但当前文档标注实验性 |
| 主要工作 | 美术管线、家具编辑器、角色空间关系 | 同样需要上述工作，另加引擎与桌面接口迁移 |
| 当前建议 | 优先做小范围样板，检验体验和资源开销 | 当内容生产与游戏系统规模成为主要瓶颈时再比较 |

官方 [spine-threejs 更新说明](https://us.esotericsoftware.com/blog/spine-threejs-runtime-update)确认可自选角色材质、接入光照和阴影。是否让角色受光应按视觉需要决定，不能把更强光照当成必然更好看。

截至本次调研，官方 [spine-godot 文档](https://us.esotericsoftware.com/spine-godot)已提供实验性的 SpineSprite3D，直接渲染平面骨骼几何；[发布说明](https://us.esotericsoftware.com/blog/spine-godot-native-3d)解释了它与旧 SubViewport 贴图方式的差异。网上“Godot Spine 只能先渲染到 2D 纹理”的旧说法已不能覆盖当前能力。新运行库对我们旧导出资产的兼容性仍需实测。

仓库已经使用 Three.js 0.180.0，现有 `app/src/renderer/garden/farm-scene.js` 具备真正的 3D 渲染、透视相机与射线拾取。因此继续使用当前桌面架构有实际基础。历史 cozy3d 预览记录也能提供经验，但它没有完整家具拖放和座位交互，不应直接视为成品。

## 开工前的最小验证范围

建议下一轮单独实现并验收以下样板，本轮尚未开始：

1. 一间房、一张独立 3D 沙发、一张茶几、一盏灯、一个有坐姿的 Spine 角色。
2. 家具能拖动、旋转、替换；确认真实厚度、落地阴影、边界和碰撞反馈。
3. 角色走近、坐下、起身；换另一张沙发后仍能对齐，不漂浮、不陷入坐垫。
4. 在所有允许镜头下检查靠背、扶手、桌面与角色遮挡。
5. 两层房间总览与聚焦切换；复用模型和纹理，记录帧耗时、内存、隐藏时资源占用。
6. 单机效果通过后，再接已有多人房间，验证布局同步和座位竞争。

样板未通过之前，不继续批量生产整套家具。只有确认镜头、角色比例和座位约定之后，批量资产才有可靠标准。
